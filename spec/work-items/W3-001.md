# W3-001 — API, Runtime and Experience Boundary Contracts

Owner: Worker 3
Depends on: none
Parallel with: W1-001, W2-001

## Scope
Define contracts for:
- REST/HTTP;
- webhooks;
- trusted approval surfaces;
- runtime adapter;
- MCP;
- A2A;
- AG-UI;
- messaging;
- developer idempotency and authorization;
- frontend information architecture and authoritative state mapping;
- design-system foundations and responsive layout rules;
- environment/deployment topology and configuration contracts;
- merchant PSP connector contract.

Create conformance fixtures and contract tests.

### Stripe UX/research lab
Survey stripe.com and Stripe Dashboard surfaces relevant to PaySwap's product architecture. Use public pages first. Where a useful surface requires authentication, use the authorized browser session; never request or store passwords in repository artifacts. Pause at the authentication boundary for the user to authenticate if needed, then continue the survey.

Record dated findings for:
- navigation and information architecture;
- onboarding/workspace model;
- dashboard patterns;
- checkout/payment methods;
- Billing/subscriptions;
- Connect/platform flows;
- disputes/refunds;
- analytics/reporting;
- developer surfaces;
- agentic commerce;
- responsive/mobile;
- trust/security messaging;
- loading/error/empty states.

## Acceptance
- every mutation is idempotent;
- approval creates explicit authorization artifact;
- UI state derives from protocol state;
- adapters cannot declare finality;
- external versions are explicit;
- the repository contains a first-pass PaySwap information architecture and journey map;
- the repository contains the Stripe UX survey findings and source dates;
- frontend state mappings are defined before downstream feature UI work;
- local/preview/staging/production topology is documented;
- no secret or private account data is committed.

## Forbidden
No fake payment completion, direct provider SDK in domain code, or chat text as authority.
