# W3-003 — Execution Graph and Provider Adapter Framework

Owner: Worker 3
Depends on: W3-002, W1-002, W2-003

Implement canonical execution plan/attempt contracts, provider-neutral rail adapter interface, generalized Connector SDK/framework, PSP connector interface, external-system connector interfaces, webhook/event ingestion and provider evidence preservation.

A connector is the productized boundary to an external provider. Each connector consumes the canonical capability model from W2-003 and exposes a capability pack that can support search/read/create/update/action/subscribe/reconcile/health/disconnect/credential rotation. Provider-specific SDKs remain inside the connector.

## Connector execution contract

Implement executable connector semantics without changing the W2-003 capability vocabulary:
- preconditions and authorization requirements;
- provider/canonical state mapping;
- ProviderStateEnvelope preservation;
- required customer/user action surfaces;
- idempotency/retry behavior;
- compensation/cancellation and partial-execution semantics;
- external object identity/revision/source-of-truth;
- evidence and reconciliation;
- explicit execution mode.

The three modes are:
- PASS_THROUGH_NATIVE;
- COMPOSED_PAYSWAP;
- OPTIMIZED_MULTI_PROVIDER.

PASS_THROUGH_NATIVE must preserve the incumbent provider flow/optimizer semantically while still traversing PaySwap's protocol authorization and evidence boundary.

The PSP connector must support the pattern: merchant keeps an existing PSP while PaySwap becomes an additional payment method/processor/orchestration capability. Stripe is one adapter example; the domain must remain PSP-neutral.

Acceptance:
- protocol issues scoped execution grants;
- adapters cannot write financial state directly;
- UNKNOWN is preserved;
- provider evidence links to attempts;
- provider state required for customer action, reconciliation or audit is not flattened away;
- PSP connector cannot imply support for a PaySwap rail unless the rail/provider capability actually exists;
- connector actions preserve external object identity, revision and source-of-truth policy;
- connector failures and provider outages do not fabricate PaySwap business outcomes;
- connectors can be health-checked independently from PaySwap itself;
- a merchant can expose PaySwap through one connector rather than integrating each underlying rail separately;
- new providers can be added without domain rewrites;
- provider-native optimization/recovery is executable as a capability when selected by the Lab/Director;
- ExternalFundsPositionObservation is represented as external observation, never PaySwap custody.

### Payment execution requirements

- payment-method offers are derived from authoritative acceptance/capability state;
- payment-method translation shows the actual rail path;
- merchant settlement destination is explicit;
- refunds/disputes and recurring mandates reuse canonical execution/reconciliation;
- external PSP payment records can be ingested without claiming PaySwap executed them;
- asynchronous/customer-action-required provider states remain actionable through the trusted application surface.
