# W3-003 — Execution Graph and Provider Adapter Framework

Owner: Worker 3
Depends on: W3-002, W1-002

Implement canonical execution plan/attempt contracts, provider-neutral rail adapter interface, generalized Connector SDK/framework, PSP connector interface, external-system connector interfaces, webhook/event ingestion and provider evidence preservation.

A connector is the productized boundary to an external provider. Each connector exposes a capability pack that can support search/read/create/update/action/subscribe/reconcile/health/disconnect/credential rotation. Provider-specific SDKs remain inside the connector.

The PSP connector must support the pattern: merchant keeps an existing PSP while PaySwap becomes an additional payment method/processor/orchestration capability. Stripe is one adapter example; the domain must remain PSP-neutral.

Acceptance:
- protocol issues scoped execution grants;
- adapters cannot write financial state directly;
- UNKNOWN is preserved;
- provider evidence links to attempts;
- PSP connector cannot imply support for a PaySwap rail unless the rail/provider capability actually exists;
- connector actions preserve external object identity, revision and source-of-truth policy;
- connector failures and provider outages do not fabricate PaySwap business outcomes;
- connectors can be health-checked independently from PaySwap itself;
- a merchant can expose PaySwap through one connector rather than integrating each underlying rail separately;
- new providers can be added without domain rewrites.
